1 — THE IDEA

What problem are we solving?

Bitcoin's public record (called the ledger — the permanent notebook that records every Bitcoin payment ever made, visible to anyone in the world) shows every single payment ever made. But it never shows names — only long codes like bc1qar0s....

So police can see money moving, but not who is moving it. Criminals — ransomware gangs, darknet sellers, extortionists, money launderers — use this to hide.

Our idea

Before a Bitcoin payment reaches the public notebook, it first travels across the internet for a fraction of a second — and in that moment it carries the sender's real IP address — the internet "house address" of the sender's computer. Everyone ignores this moment. We capture it and match it back to the payment.

2 — WHAT WE USED, AND WHY

Every tool, in plain words

ToolWhat it isWhy we picked it
Rust A programming language known for being both very fast and very safe against crashes. Our data-reading code has to survive damaged/incomplete files without crashing on stage. Rust forces us to handle every error instead of guessing.
Python The most common language for data science and AI. Everything after the raw parsing — clustering, graphs, the AI model, the dashboard — is Python, so the whole team can read and edit it.
DuckDB an embedded database — a database that lives inside a single file, with no separate server to install or run We needed to store and search millions of transaction records fast. DuckDB does this without needing a database server — perfect for a laptop with no internet.
Parquet a file format for storing tables of data very compactly and very fast to search Our stored data (millions of rows) needs to load in milliseconds, not minutes. Parquet is the industry standard for this.
GeoIP database A downloadable file that maps an IP address to a country and network provider. The problem statement explicitly asks for this. We use a free one called DB-IP, stored inside our own project — no internet needed to use it.
scikit-learn The standard Python library for building AI/ML models. Builds our two detection models — explained in Stage 5 below.
SHAP a library that explains an AI model's decision — showing exactly which input caused how much of the final score The problem statement demands "explainable" results. SHAP is how we turn a plain number like "0.91" into "0.91 because of X, Y, Z".
Streamlit (building now) A Python tool that turns a normal Python script into a website/dashboard, with no separate web-development work needed. Lets us build the investigator's dashboard fast, in the same language as everything else.

Why offline matters (the most important rule)

The problem statement says the whole system must work with zero internet connection. That's why every choice above avoids anything that needs a server or a live internet call — the GeoIP file is downloaded once and stored inside our project, DuckDB needs no server, and our own code never calls out to the internet.

3 — THE SIX STAGES

How data flows through the system

📖 Follow one case through all six stages

To make this real, we'll follow one made-up case from start to finish:

The scenario: A hospital's computers get locked by ransomware. The attacker demands 2 BTC to unlock them. The hospital pays. That 2 BTC now has to travel through the criminal's hands, get cleaned, and eventually turn into real cash — and every step of that journey leaves a trace in our system. Watch how each stage below catches a different part of the trail.

Each box below is one folder in our code. Data flows left to right, one stage feeding the next.

Stage 1 — The Generator (folder: generator/)

The problem statement says no real data will be given to us — we must build a fake (but realistic) dataset ourselves. So we wrote a program that pretends to be a small Bitcoin network: 74 fake people (normal users, exchanges, and criminals), all sending each other money over 45 days.

Real-life example: like a flight simulator. It's not a real plane, but every dial and reaction behaves like a real one — so training on it actually prepares you for the real thing.

Why this is actually an advantage, not a limitation

Because we planted the criminals, we know exactly who they are. That means we can check our own answers — "did the AI actually catch the criminal we planted?" — instead of just guessing that it works.

Result: 12 out of 12 automated checks pass — including a check that if we break the simulation on purpose, the check correctly starts failing (proving the check isn't fake).

Where our story begins

Among our 74 fake people, we planted 3 "ransomware" actors — exactly like the hospital attacker. One of them, entity E-0066, receives ransom payments and then tries to launder them. Because we planted this actor, we secretly know the full truth: which wallets are theirs, which IP address they broadcast from, and every step they took to hide it. The rest of this page is about whether our system can figure that out without being told — using only what a real investigator would see.

Stage 2 — Ingest (folder: ingest/)

This is the program (written in Rust) that reads the raw files — CSV, JSON, XML — and turns them into one clean, fast-to-search format. It also looks up each sender's country using the GeoIP file.

Real-life example: like airport immigration. Every passenger comes from a different country in a different format (different passports, different languages) — immigration turns all of them into one standard entry record, and stamps their nationality.

40,000+records / second
0crashes on broken files
11/11checks passing

We deliberately fed it broken, corrupted files (missing data, wrong numbers, truncated files) to prove it never crashes — it just skips the bad row and reports it, exactly like a real forensic tool must.

Our case, at this stage

The hospital's ransom payment — and thousands of other unrelated payments happening at the same time — arrive as raw CSV/JSON/XML files. Ingest reads all of them, in whichever format they came in, and turns E-0066's ransom transaction into one clean row alongside everyone else's. At this point it's just one row in a huge pile — nothing marks it as suspicious yet.

Stage 3 — Cluster (folder: cluster/)

One person often uses many different wallet addresses. This stage groups scattered addresses back into the real entity that controls them, using two clues:

  • Clue 1 — spent together: if 4 addresses pay one bill together in one transaction, one person owns all 4 (like paying a restaurant bill using notes from 4 different pockets of the same coat).
  • Clue 2 — the "change": if you pay ₹40 with a ₹100 note, you get ₹60 back — that's still your money, just at a new address. We detect which output is "change" vs a real payment.

The one trap we had to avoid — CoinJoin — when many strangers deliberately combine their payments into one transaction to confuse investigators, like 50 people all dropping identical ₹500 notes into one hat

If we blindly applied Clue 1 to a CoinJoin, we'd wrongly merge innocent strangers into our suspect's group. So we detect and skip these first. Result: 100% detection, 0 false alarms.

Result: 6 out of 8 checks pass. The 2 remaining are a known, honest trade-off between being extra careful (fewer false groupings) vs finding more connections — explained more in section 4.

Our case, at this stage

After collecting the ransom, E-0066 doesn't just sit on it — the wallet quietly makes several more payments over the next few days, each from a slightly different address. Clue 1 catches some of these because a few payments spend from more than one address together. But most of E-0066's laundering happens through single-input hops, which Clue 1 and Clue 2 alone can't fully connect — this is exactly why we need Stage 4 next.

Stage 4 — Graph (folder: graph/)

Money launderers often "peel" money — send a big pile of Bitcoin through 20-30 tiny hops, shaving off a small slice each time, to look boring and avoid detection. (Real-life name: salami slicing — stealing a little bit at a time so no single slice looks suspicious.)

Clustering (Stage 3) can't see these chains — each hop looks unrelated on its own. So we built a second detector that follows the money as a path, hop by hop.

Before this stage, a criminal who made 31 payments looked like 30 separate, unrelated people. After it, they correctly show up as one entity with 20 connected payments — which is what finally makes it possible to build a strong case against them in Stage 5.

Our case, at this stage

Now we follow the hospital's 2 BTC as it "peels" — a small slice goes to a fake shop (cashed out), the rest carries forward to a brand-new address, over and over. Stage 4 walks this exact path, hop by hop, and stitches all 20+ of E-0066's scattered hops back into one single trail. Before this stage, our system thought it was watching 20 different strangers. Now it knows it's one entity — the same criminal, moving the same ransom money.

Stage 5 — Fusion ⭐ (folder: fusion/) — this is our main idea

This is the heart of the whole project — matching a wallet (Stage 3+4's output) to the real IP address that broadcast its payments.

  1. For each payment, we look at every "sensor" (listening computer) that heard it, and note who heard it first.
  2. If the same IP address is consistently the "first to hear" a suspect's payments — again and again, many times — that is not a coincidence.
  3. We calculate exactly how unlikely that coincidence would be by chance (a p-value — a number from statistics that says "how surprising would this pattern be if it happened purely by chance?" — the smaller the number, the less likely it's a coincidence), and only call it a real lead if it's extremely unlikely to be random.

The mistake we caught ourselves — and fixed

Our first version found 176 "confident" leads. To test it honestly, we scrambled all the wallet-to-person answers randomly (so there should be zero real patterns left) and ran it again. It still found 41 fake "confident" leads — proof our math was wrong, because we were testing hundreds of guesses at once and some pass purely by luck (like flipping 100 coins — a few will land on 10 heads in a row by pure chance).

We fixed the statistics (called a Bonferroni correction — a way of being extra strict when you're making hundreds of guesses at once, so lucky coincidences don't get mistaken for real patterns) — and the scrambled test now correctly finds zero fake leads, while our real leads stayed just as strong.

Our case, at this stage — the payoff

Every one of E-0066's 20+ payments briefly touched the internet before reaching the ledger, and our sensors recorded who "heard" each one first. This stage adds it all up: one specific IP address was first to hear 30 of E-0066's 37 payments. For that to happen purely by chance would need a coincidence with roughly 54 zeros after the decimal point in its probability — in plain terms, essentially impossible unless that IP really is where the payments came from. This is the moment a wallet address stops being anonymous and becomes an internet address a real investigator could act on.

Stage 6 — AI Models (folder: models/)

We built two AI models that work together:

Model A — RandomForest

A supervised model — we show it examples of known criminals and known innocent people, and it learns the pattern. Good at catching known crime types.

Model B — IsolationForest

An unsupervised model — nobody tells it what's "criminal". It just flags anyone who behaves very differently from everyone else. Good at catching brand-new, never-seen-before crime patterns.

How we know the AI isn't cheating (memorizing instead of learning)

We scrambled the "criminal / not criminal" labels randomly and re-tested. A model that's just memorizing would still score well on scrambled data. Ours dropped from 94% accuracy to 1.6% — proof it's genuinely learning real behaviour, not memorizing.

Explainability (SHAP): every flagged entity comes with the top reasons, e.g. "flagged because: sends money too often (34%), payment chain matches a peeling pattern (11%), active at unusual hours (9%)" — a real officer can check this reasoning instead of trusting a black box.

95.8%precision (cross-checked)
92.0%recall
9/9checks passing

Our case, at this stage — the ending

By this point, E-0066 has a risk score close to 1.00 (maximum). Model A recognises the pattern as matching known ransomware behaviour. Model B flags it independently for simply not looking like anything normal in the whole dataset. And SHAP prints the exact reasons: heavy transaction activity, a chain-shaped peeling pattern, and unusual timing. An investigator opening this case doesn't see a mysterious "0.98" — they see: "flagged because of X, Y, Z, and here is the IP address, with this much confidence." That's the entire pipeline, start to finish, on one made-up hospital ransom case.

The one honest trade-off (clustering)

Being extra careful about grouping wallets correctly (99% precise — almost never wrongly merges two different people) costs us some completeness (only 15% of possible connections found). We chose "careful but incomplete" over "complete but sometimes wrong", because a wrongly accused innocent person is a much worse outcome than a missed connection.

5 — HOW TO ACTUALLY RUN IT

Running the whole pipeline, one command at a time

This is the order every stage runs in. Each one reads what the previous one wrote.

#CommandWhat it does
1python generator/generate.py --out dataCreates the fake dataset
2strata-ingest data/*.json --geoip data/geoip --out storeReads it into fast storage
3python cluster/run.py --store storeGroups wallets into people
4python graph/run.py --store storeFinds laundering chains
5python fusion/run.py --store storeMatches wallets to IP addresses
6python models/run.py --store store --data dataScores risk + explains why

After all six, every result is sitting in the store/ folder as fast, ready-to-read files. The dashboard we're building now simply reads this folder and displays it — it does not need to redo any of the above work.

6 — HOW WE WILL DEMO IT

What the judges will actually see

  1. Switch off the WiFi, visibly, in front of the judges. This one action proves our whole "works fully offline" claim without saying a word.
  2. Run all six stages in front of them (or show it pre-run, since it takes a couple of minutes).
  3. Open the dashboard. Show the ranked list — most suspicious entity at the top, with a confidence score.
  4. Click on the top entity. Show the connected wallets (Stage 3+4), then the matched IP address with its confidence (Stage 5), then the AI's reasons (Stage 6).
  5. Say the honest version, always: "This is a lead, not proof — with a confidence score and clear reasons, exactly like the problem statement asked for."

The 30-second summary to memorize

"Bitcoin shows the money but hides the person. The internet briefly shows the person but not the money. Everyone else only looks at the money. We look at both — and we do it with the internet switched off."
